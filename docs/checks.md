# Checks and the gate

How a change is checked on the machine that pushes, and what holds the check honest. The map of the repository is `CONTRIBUTING.md`; the numbers in parentheses are decisions in `docs/architecture.md`.

## The cycle

A change meets six moments, each with one question and one owner. A tier's wall time is judged against a row of `gate/budgets.yaml`, and this page never states the number, so it cannot go stale (gates.command.17, gates.command.31).

| Moment | Its question | Owner | Tier in `Taskfile.yml` | Budget row |
|---|---|---|---|---|
| Commit | Does the staged change read and never rewrite (format, `go mod tidy` as a diff; the generated files are the push's, gragas#2228), and hold no secret (gragas#698)? | the builder, on their machine, by the pre-commit hook: `task pre-commit` | `pre-commit` | `tier-pre-commit` |
| Push | Does the pushed tree pass the commit-level members? | the builder, on their machine, by the pre-push hook: `task pre-push` | `pre-push`: the commit checks, build, vet, the lint of the diff and the secrets | `tier-pre-push` |
| Review | Does a second reader, who did not write it, find a hole? | the reviewer agents | none: it holds no member | rounds, not seconds |
| Landing | Does the merged candidate pass once? | the lander, by its card: `gragas-dev landing run`, which runs `task landing` on the merged tree (gragas#2169) | `landing`: the push tier, then `warm`, which compiles full's tests and runs none, then `full`, every member the push leaves out, then the goldens journeys afresh | none of its own: the push tier's, `tier-warm`'s and `tier-full`'s lines run inside it |
| Release | Does a fresh clone of the tag pass the push and full members and what only a release proves? | the hub | `release` | `tier-release` |
| On demand | The long fuzz run and the heavy race run: what does a long run find? | whoever asks; nothing waits for it | not a tier | none |

A builder's hand-in is the push tier. `full` holds every member the push leaves out: landing runs it on the merged tree after the push tier. One machine proves a change. Nobody runs a later moment's tier as their hand-in, and no moment has a tier of its own below push. A member that cannot meet its tier's budget moves only to a later blocking tier, never to a timer, never to on demand and never out of the gate.

What is built and what is only designed (docs.freshness.4): the pre-commit hook runs the check-only members; the pre-push hook runs the push tier; `full` runs the members the push leaves out, at landing; the release tier holds the members that prove only a release; the fuzz run (`gragas-dev fuzz`) and the heavy race run are on demand, which no tier runs; the landing check is `task landing`, which runs on the merged tree. The push and full test what they change (gragas#970): `test` runs from Go's test cache, and `test-uncached` runs the same packages shuffled and uncached at release; `secrets` reads the commits past origin/main, never fetched, and `secrets-full` every tracked file and every commit at release; `journeys-smoke` runs one journey test per command in the tree (`internal/journeys/smoke.txt`), and `test-heavy` every journey at release; `gate-tests` runs the gate's own packages, `cmd/gragas-dev` and `cmd/gragas-new`, at release, with no path filter and run again (`-count=1`). It ran over the push budget on a change to the gate, so it moved (#910, RULED); nothing is dropped. The review carries the guard the push held: on a pull request that touches `gate/`, `cmd/gragas-dev` or `cmd/gragas-new`, the reviewer runs `gate-tests` at the head and quotes its footer, and a MERGE without that footer is not a MERGE for such a pull request. #911 deleted most of `cmd/gragas-dev`, so the member is to be measured again; if it fits push, it comes back. No member yet reports what it ran, and no member declares where it can run; the DCS tickets of `docs/self-check.md` close those.

The six decisions of the standard (d1 to d6), as they bind gragas:

- **d1.** No retry closes a red. One diagnostic rerun on a quiet host is logged, the first red opens the issue, a second quarantines the test with an owner and an expiry. The quarantine list is not built (#702).
- **d2.** The shared tier command is the shared kit's, built from a pinned tag. gragas runs its tiers as tasks of `Taskfile.yml` (go-task) until the shared kit's `tier` block exists.
- **d3.** The package that reads the tree leaves the push race run; the on-demand race run covers it (#703).
- **d4.** Release runs the light race set as push does; the heavy race run is the hub's daily on-demand run on main. It is at home on demand (#647); the daily run is not built.
- **d5.** A post-land run of the whole tree is retired wherever landing proves the whole merged tree. gragas has no post-land run.
- **d6.** No declared test selection yet (#910). The push's `task test` runs the light packages from Go's test cache, unshuffled, and `task test-uncached` runs them shuffled and uncached at release (gragas#970; `docs/self-check.md`, tests.selection.1).

## Setup

- Go 1.27.1, toolchain 1.27.4: `go.mod`'s toolchain line fetches it.
- The platform's libraries (go-console, go-files, go-proc and go-run) are private modules. Once per machine: `go env -w GOPRIVATE='github.com/birdtable/*'`, and git must be able to read those four repositories the way your clones of the birdtable repos do. Nothing falls back to a copy. That setting reaches `task tools` and your own go, never a test: a go a test starts runs with `GOENV=off`, `GOWORK=off` and `GOPROXY=off` and is handed no `GOAUTH`, `NETRC`, `GOFLAGS` or `GOPRIVATE` (`internal/config/testing`, gragas#1450), so it fetches nothing, and a module missing from the cache is red and names `task tools`, which fills it.
- The trust walk (`internal/host/trust`, over go-files' `trust`, at go-files v0.4.0) needs Linux 5.8 or later, for `openat2` (gragas#1451, R7). Below it, or where a seccomp filter refuses `openat2` with `ENOSYS`, it fails closed: every name on tmpfs, overlayfs, FUSE, NFS, 9p, btrfs or ZFS is refused, `$XDG_RUNTIME_DIR`, `/dev/shm` and a container's own overlayfs root among them, and a filter that refuses it with `EPERM` leaves such a name an error. A gate host or a namespace container below that floor, or without `openat2`, cannot run the tiers. On Linux a name's owners are judged only on the file systems go-files judges: ext2/3/4, xfs, btrfs, f2fs, ZFS, tmpfs, ramfs, overlayfs, FUSE and NFS. A name on any other, as CIFS, 9p, vfat, exfat, squashfs or erofs, is refused with `ErrMount`. gragas adds no type to `Who.FileSystems`, so these stay refused, failing closed, and `internal/host/trust` answers them as not this account's (owned.go). So a work tree, a temp folder or a tool on such a mount is refused by name.
- The browsers of the explorer's Vitest browser mode (Chromium's headless shell and WebKit, gragas#998) are placed by Playwright's own `playwright install`, run by the pinned node at the version `explorer/pnpm-lock.yaml` holds, into `.tools/playwright` (`task tools`). Neither the CDN nor the npm package publishes a checksum, so `tools.yaml`'s `browsers:` block pins one digest of the browsers' folders, measured over https when it was pinned: a first-fetch pin, not signed by the publisher (supply.provenance.7). `gragas-dev browsers` holds the folder to it: each browser folder is summed by go-files' `treesum` (package `internal/host/treepin`, its one owner) and the names and sums are summed again; Playwright's `.links` folder, which holds the absolute path of the clone and so differs between two clones, is left out, and a file or a link beside the browsers' folders is refused. `treesum` follows no link, takes a link whose target stays inside the folder, and refuses a link out of it, a loop, a device, a second name for a file and a folder past its caps. A changed or added file is refused before a test starts a browser. The pin is listed for the platforms measured so far (a platform with none refuses, naming the missing pin, and a Linux pin waits for two sessions that print the same digest); another platform is measured with `gragas-dev browsers --print --platform <os/arch>` and added. The digest is `browsers2:` since go-files v0.4.0, whose `treesum` lines are `t2:` and no longer cover the executable bit (content is still pinned); `treepin.Check` refuses a `browsers1:` pin as an older format, to be measured again, before it walks. A new pin is measured twice from a tree the old binary has just passed against its `browsers1:` pin on that system, or from two fresh fetches that agree, never from whatever is on disk, which would bless drift into a first-fetch pin (gragas#1451). Only `task tools` passes `--unmeasured-ok`, with which the check ends green on a system whose browsers row says unmeasured (gragas#1984); every member that runs a browser first checks the pin with `--platform` and nothing else, in an entry of `cmd` and `timeout` alone (no flag, no other folder, no refusal swallowed in the line or by `ignore_error`, no `platforms` and no `defer`), so a browser never runs from a folder the pin did not check. A member is known by naming Playwright: a command line that does, or a key or a value of anything else the task holds, its `env` and `vars` among them; the file's own `env` and `vars` reach every member, so they may not, and the file has no `dotenv` and no `includes`, which bring in what the test cannot read. A member carries only `cmds`, `deps`, `desc`, `env`, `status` and `vars`, a closed set each for its reason, so `ignore_error`, `platforms`, `dotenv`, `dir` and a key nobody named are refused. Neither its own `vars` nor a call of it, at the top of an entry or under `defer`, sets a variable the pin check reads (`GATE`). A call names its task as written, never by a template, and no member's name holds `*`, which go-task matches to a call of another name. Its `env` holds `PLAYWRIGHT_BROWSERS_PATH` alone, as a plain string, since a member's env reaches the pin check's own `go run`. That value is `{{.ROOT_DIR}}/.tools/playwright`, the folder the pin check reads (`browsersFolder` in `cmd/gragas-dev/browsers.go`). Every other line that names the variable sets it to the same folder, the run line's `--env` and the tools step's install among them, so a browser never runs from a folder the check did not read (gragas#2107). No `status` line and no `sh:` value of the member names Playwright, since go-task runs them before the first command. So nothing the member holds makes the pinned text run another program (gragas#2066); the file's own `env` reaches every member too, and it is held to the table under "What the Taskfile's env and vars may set" (gragas#2107). A member that names Playwright nowhere is not seen. `TestTheBrowsersLinesOfTheTaskfile` (`internal`) reads `Taskfile.yml` as data and holds both (gragas#2006).
- go-task is the one tool you install by hand: build it from the pinned `tools/` module (`go build -C tools -o ../.tools/bin/task github.com/go-task/task/v3/cmd/task`), then `task tools` builds every other pinned tool into `.tools/bin`. No tier runs `task tools`: it needs the network and installs pnpm packages, so you run it once per clone and again when `tools-check` names it. `tools-check` starts the pre-commit tier, and so every push: it checks every pin in one process, is red when a tool is missing from `.tools/bin` or is not the pinned build, or when the `node_modules` of `explorer` or `tools/.node` (the Taskfile's `PNPM_TREES`) is not the install of its lockfile (`explorer/pnpm-lock.yaml`, `tools/.node/pnpm-lock.yaml`) (the copy pnpm keeps in `node_modules/.pnpm/lock.yaml` is not the lockfile's packages document), names `task tools` as the fix, and never installs one, so neither a commit nor a push needs the network (supply.install.10, gragas#1215). That pnpm check holds the lockfile copy pnpm wrote, not the installed files: a file edited by hand under `node_modules` passes it, where a `--frozen-lockfile` install would have relinked it from the store; `task tools` does that.
- No release-age window is held, by gragas or by a project that takes its rules: supply.age.1 and supply.age.2 are retired, `gragas-dev age` and the member `supply-age` are gone, and both pnpm workspaces set `minimumReleaseAge: 0` (pnpm 12 holds a one-day window of its own when the key is absent, and writes a `minimumReleaseAgeExclude` entry for a younger release, so the window is off by the key). A pin younger than seven days installs and passes the push tier. Exact pins, lockfile-only installs, no install scripts, the licence list and the scans stay.
- Arm the hooks once per clone with `task hooks`, the one sanctioned way (gragas#1220): it sets `core.hooksPath` to `hooks`, this repository's own folder, and to nothing else, takes no variable, and stops where another path is already set rather than replace it. A worktree of the clone inherits it, so a shared clone is armed once. `task armed` is red in a clone that is not armed, and names `task hooks`; it also holds both hooks committed as programs. The committed agent settings refuse an agent every `git config`, every `git -c` and `--config-env` after any word and in any letter case of the key, and a write to `.git/config` or a worktree's `config.worktree` (gragas#2110); The cases of those globs are checked outside this repository. The hooks then are the committed files of `hooks/`, never a copy. Each runs the clone's own `.tools/bin/task`, `pre-commit` or `pre-push`, from the root of the work tree, and stops with the line to build it when it is missing. The pre-push hook checks the tree of each pushed ref, in a throwaway worktree at that commit when it is not the clean HEAD. That tree gets this clone's `.tools` by a link, and its own `node_modules`, the explorer's and `tools/.node`'s, from `task tools-pnpm`: the two installs of `task tools`, run by the hook with `pnpm_config_offline=true` and `pnpm_config_store_dir` set to the store the clone's explorer install recorded in `node_modules/.modules.yaml`, so the push still needs no network (gragas#1522). pnpm refuses a linked `node_modules` (gragas#1033). Where that file names no store or the offline install fails, the push is refused and names `task tools`. No other task writes git config or .git/hooks. `task tools-check` holds each go tool of `.tools/bin` to the module, version and sum of `tools/go.sum`, and every dependency and replacement `go version -m` names to a line of it (a binary built on other dependencies is stale), and golangci-lint, a release program, to the sha256 `tools.yaml` pins (`gragas-dev fetch`): a stale binary is red, and `task tools` replaces it. Its go tools' part, `task tools-go` (`gragas-dev tools-go`, Go since gragas#1655, so it runs the same on every system), removes a go tool that fails those checks before building it again with the stated build of `tools.yaml`'s header, since `go build` writes nothing over a target whose build ID it reads as current, and a file changed past its build ID would otherwise stay (gragas#1480). A go row of `tools.yaml` that pins no sha256 for the system the check runs on and gives no `no-sha256` (nor, on Windows, `no-windows`) reason, or whose `platforms:` line is not one well-formed sha256 pin, is red and named.
- Every check tool is pinned in `tools.yaml` by version; the go tools are built from the `tools/` module's lock, and a node tool (eslint, tsc) is a package of the `tools/.node` workspace, installed by the pinned pnpm and node from its lockfile with no install script. Nothing comes from your PATH and nothing is `go install`ed.

## Checks

**The gate runs on the machine that pushes.** Actions minutes cost money, so every check runs there. The one workflow, `.github/workflows/test.yml`, is the proof on the hosted runners: `go vet` and `go test` on Linux and Windows for a pull request, and on macOS too for main and a tag. It is no part of the gate. **Run `task pre-push`**: `tools-check` (it fetches nothing: a person runs `task tools` when it names it), the checks the pre-commit tier also runs (format, explorer format, boards, tidy), and the generated files and `os-code`, which only the push runs (gragas#2228), build and vet for every system in the list, golangci-lint on every system over the lines changed since the merge base with origin/main, and the secrets in the commits past origin/main (in the tracked files and all of history at release): the commit-level checks alone. **`task full` runs the rest**: the wide-package guard, `gragas check` over the rulebook, the gate registry, the known vulnerabilities, the release-age window with the module proxy off, the licences and the whole-tree lint for every system in the list, the race tests (from Go's test cache at push, where the slowest groups of the repository's own checks, `NO_RACE_PUSH`, run without `-race`; shuffled, uncached and all under `-race` at release), the journey smoke list and the goldens, the explorer's typecheck, lint and tests, the subset build. Landing runs it after the push tier, on the merged tree on this Mac. **The pre-push hook (`hooks/pre-push`) runs `task pre-push` before every push**, on the tree each pushed ref carries, and refuses the push when it fails. Each hook is one line, `go run ./cmd/gragas-dev hook <tier>` with the Taskfile's own GOFLAGS and GOWORK, so the same Go runs it on every system (gragas#1655). A person's `git push --no-verify` skips it, and the push says why; the committed agent settings refuse it, a hooks-path override and the hook-disabling variables. A glob matches text, so a split word, git's name in a variable, a script or another case, or a relative path to the config file gets past it: the hook, and landing on the merged tree, are the guard. The hook hands a git or a task it starts an allowlist of the environment it was given and drops every other name, in any case (gragas#2181). The allowlist is three sets: the names go-proc gives for what a child needs on this system, the names go-proc gives for the person's home, configuration, cache, state and temp folders (so go's caches stay where they are and a landing finds them warm), and one table in `cmd/gragas-dev/hook.go`, `hookKept`, that gives each of the gate's own names its reason: go's three private-module names, the ssh agent, the certificate and proxy names a fetch needs, the terminal's and `GATE_WEIGHT`. `GIT_INDEX_FILE` is on none of them: git names it to the pre-commit hook alone, which hands it to `task pre-commit`; at pre-push and at landing it is the caller's, and an index of theirs (one at the base, or an empty one) would make a changed input read as unchanged and empty a member's list of files, so neither the hook's own git nor a member is given it. So git's `GIT_CONFIG_COUNT` and `GIT_CONFIG_PARAMETERS`, go's `GOFLAGS`, `GOMODCACHE`, `GOCACHE` and `GOEXPERIMENT`, and every tool's switch reach no member, and a name a member needs that the table leaves out turns its tier red, never green. Every go a member runs has `GOENV` off, so it reads no file of go variables, a cache program among them. `GOPRIVATE`, `GONOPROXY` and `GONOSUMDB` are read once by `go env`, with the caller's `GOENV` left out, so they come from the person's own `go env -w` file at its default place; only those three are handed on, and `go.sum` with `-mod=readonly` still verifies every module. The tools' switches are named by the prefix each begins with (gragas#2161): `TASK_` (go-task reads each flag from one, and `TASK_DRY` prints the tier, runs none of it and exits 0), `GOLANGCI_` (golangci-lint's diff patch keeps no finding outside its hunks), `PNPM_CONFIG_` and `NPM_CONFIG_` (pnpm's script-shell picks what a script runs under), `NODE_OPTIONS` (a preload), `GOCACHEPROG` (a program that answers for the test cache) and `GOENV` (the file go reads any variable from that the environment does not set, a cache program among them). A caller who sets one for a commit or a push changes nothing the tier runs; the settings refuse the line as well, and `[gap]` holds the spellings with no `=` or a split name. The landing is cut the same way (gragas#2169, gragas#2181): `gragas-dev landing run` starts the clone's `.tools/bin/task landing` through the same function, and `landing begin`, `check` and `merge` refuse, naming it, while a variable of one of those prefixes is set, so a person who exported `TASK_DRY` and ran `task landing` directly, which prints the landing and exits 0, is stopped at the merge. A switch set for the one command (`TASK_DRY=1 task landing`) is caught by neither: go-task runs no command under it, `landing begin` included, and the merge's own environment does not hold it. The landing's instructions name `landing run`, and that is the guard. A tool's own file of settings under the home (an `.npmrc`, a `.taskrc.yml`, a `.gitconfig`) is not cut, and neither is PATH, so a `go` earlier on it runs every member.

**Write a commit message to a file and commit with `git commit -F <file>`.** The deny rules of the agent settings are globs, and a glob matches anywhere in the command line, the `-m` text included. A message that names a flag starting `-n`, or quotes `--no-v`, is refused though it skips nothing, and the agent sees a refusal with no hint why. The globs stay wide on purpose: a narrower one reopens spellings that were closed, and the pre-push hook is the real guard.

The pre-commit hook runs the check-only members (format, go mod tidy's diff, explorer format and the boards; `os-code` and the generated-files diff are the push's, since the commit tier was over its budget with them, gragas#2228) and the commit's own (gragas#698), each of which reads the stage the commit is built from: the index `GIT_INDEX_FILE` names when `git commit -a` or a commit of named paths built it.

- `secrets-staged`: the pinned gitleaks over every file the stage adds or changes, read from git's objects. An edit not staged is not read here, and no push sends it; the release tier's `secrets-full` reads it.
- The secret scan is one task, `secrets-scan` (gragas#1156), whose pass is `gragas-dev secrets` (gragas#1655: Go, so Windows runs the same judgement and git's log is read as a stream, with no temp file), which `secrets-staged`, `secrets` and `secrets-full` run and `internal/secrets_test.go` plants through. It reads only what git tracks: the stage, the commits of a range, or every tracked file as it is, each made a commit no ref names, so a file nobody added, such as build output git ignores, is never read and needs no allow-list. It runs twice: `.gitleaks.toml` brings gitleaks' default rules and two of ours, and `.gitleaks-key.toml` the private-key rule alone, because gitleaks 8.30.1 appends its default path allow-list (`go.sum`, images, any `gitleaks.toml`) to every config that extends the defaults, with no key to drop it. So the pass refuses a path of the scan, other than the root `.gitleaks.toml`, whose name holds `gitleaks.toml` (an access key in a gitleaks.toml of a folder was read by neither pass). An allow comment, a `.gitleaksignore`, a shallow clone, a grafts file, a `-diff` attribute, a NUL byte or a merge's own lines hide nothing, and a pass whose git wrote an error is red. So is a pass in which gitleaks says it scanned fewer or more commits than git's own log of the range holds with a hunk, the count the history scan held before #911.
- A canary holds the first pass to its rules (gragas#1314): `internal/secrets_canary_test.go` runs `secrets`, `secrets-full` and the tree pass over a clone holding a made-up token in the shape of gitleaks' default `github-pat` rule, which only `.gitleaks.toml` finds, and each must be red naming the rule and the file. The private-key plants cannot hold that pass, since the second pass finds a key alone. Four plants prove the check, each a `.gitleaks.toml` beside a copy of the Taskfile that leaves the members green: an allow-list path, a stopword, an empty rule set, and the default rules dropped.

The tier runs with `GOPROXY=off`, for every member: go-task gives a called task the file's `env:` and never the calling task's, so the setting is the var `NO_NETWORK`, which the tier and each task of it passes to the tasks it calls, and the file's `GOPROXY` reads it (gragas#1313). `TestEveryGoCommandOfTheCommitRunsWithTheNetworkOff` runs the tier with a go that records its `GOPROXY`, and plants a call that does not pass it.

## The tiers

`Taskfile.yml` is the four tiers, `task pre-commit`, `task pre-push`, `task full` and `task release`. Each tier runs its preflight in order (`pre-commit` checks the tools are built; `pre-push`, `full` and `release` build them, and `full` and `release` run the wide-package guard), then its members as deps of one internal task (`pre-commit-members`, `pre-push-members` and `push-checks`, `full-members` and `full-checks`, `release-members`), side by side, then the budget. `pre-push` shares the check-only members of `pre-commit` (`commit-checks`) and leaves the staged-file members out; `full` holds every member the push left (gragas#1619), and the two hold no member twice; `release` takes `push-checks` and `full-checks` and adds the release members, and the cached `test` of full is not among them (`test-uncached` is), nor the push's lint of the diff (the whole-tree `lint` is). A member that is red names itself, and the others still finish. `vuln`, `licences` and `vet` run one dep for each system of the list (go-task's `for` over `CROSS`), each a `-system` task that names the system when it is red. `task release-recipe` runs the release tier and then the recipe's own steps, and `task release-publish` publishes from the tag (`docs/self-check.md`, Releases). go-task and hatch are pinned tools (`tools.yaml`), run from `.tools/bin`; every test member runs go test through `hatch tests`, which is red when go test fails, when no test ran and when every test skipped, and kills the run at `TEST_TIMEOUT` (#1471). Every `cmds` entry of a task has a `timeout:` (go-task ignores one on the task itself, and the audit refuses it), none starts a background command, and every `go test` line passes the one `-timeout {{.TEST_TIMEOUT}}` (gragas#1135).

Each tier task records its start and ends on `hatch budget --cpu --tier <name> --since <start> -- task <members>` (hatch v0.6.0, a go tool of `tools/go.mod`; the Taskfile's `BUDGET` var holds the line), which runs the tier's members in a tree of its own and holds the user plus system time of that tree to the tier's `cpu_limit` in its row of `gate/budgets.yaml` (`tier-pre-commit`, `tier-pre-push`, `tier-warm`, `tier-full`, `tier-release`), and fails over it. The budget measures what a tier costs, in CPU-seconds: a waiting tier costs no CPU, so the room and a wait for the disk decide nothing, but CPU time grows with the load the machine is under, so a `cpu_limit` holds at the load a push meets and not on a quiet host (gragas#1779). `tools-check`, which runs before the members, is outside the measure. The row's `limit` is the wall time, and it is a hang guard only: a tier over it with its CPU under passes, and a command still running at ten times it is killed and red as hung. hatch prints the CPU time, the wall time and the load, so a red says which it was. Nothing is sampled before the tier and no overrun is forgiven; the limit is set at the load a push meets. `warm` compiles every test package `full` runs, `-race` as `test` runs them, with `go list -export -test -deps`, which links and runs nothing; landing runs it right before `full` and the release right before its members, so `full`'s line times the tests and the cold compile is `tier-warm`'s, whose limit cites the measure it is set from (gragas#1663). A run over its `cpu_limit` fails: move the heaviest member to the next tier, never skip it. A `cpu_limit` is set from at least three runs of the tier on the Mac with headroom, and the numbers are in the pull request that sets it; the member timeouts are a second guard, wall time against a hang, never a measure of cost. A tree that hatch cannot read whole (a descendant that outlived the command) is red and never passes. No stamp is written and none is read: a tier runs every time.

What differs from the Makefile members, each held by a test in `internal/taskfile_test.go`:

### What the Taskfile's env and vars may set

The file's `env` reaches every command of every member, its `go run` lines among them, and a task's `env` reaches each of its own commands, so a key such as `GOFLAGS` (`-overlay`), `PATH`, `GOTOOLCHAIN` or `GOENV` would run another program under a pinned line. `GATE` and `TOOLS` name the programs the members run. So both are held to this table (gragas#2107), which `TestTheEnvAndTheHeldVarsOfTheTaskfile` (`internal`) reads:

- Every key that the file's `env` or a task's `env` sets is a row of the table, at the row's value, as a plain string. A `sh:` value would run a program as go-task compiles the task, and a `ref:` value would read another variable. Every row of the file's `env`, of its `vars` or of one task is set.
- `GATE` and `TOOLS` are set only by the file's own `vars`. A task's `vars` may not set them, nor may a call's `vars` (at the top of an entry, under `defer`, in `deps`, by any name or by a template), nor a `for`'s `as`.
- A task's `vars`, a call's `vars` and a `for`'s `as` may set only the keys of the table's `tasks.*.vars` rows, at any value. They replace the file's var of that name for every line of the task called, and several of the file's vars are whole command lines or the flags of one: `GOFLAGS_GUARD`, `BUDGET` and `HATCH_TESTS_FLAGS`. Holding the keys by name holds every var the file adds later too. A `tasks.*.vars` row that no task or call sets is red.
- No `vars`, call or `as` names a variable that go-task sets itself (`ROOT_DIR`, `TASK`, `CLI_ARGS`, `ITEM` and the rest). Setting one would replace it for every line that reads it.
- The file and its tasks have no `dotenv`.

The test's comment cites go-task v3.54.0's source for each path, by file and line. A value the caller's own environment holds wins over the file's (go-task's `ENV_PRECEDENCE` experiment is off), which is why each tier's first step refuses a caller's `GOFLAGS`, `GOTOOLCHAIN`, `GOWORK` and `GOPROXY` (`GOFLAGS_GUARD`). Where is the key's place: `env` and `vars` at the top of the file, `tasks.<name>.env` in that task, `tasks.*.env` in any task, and `tasks.*.vars` in any task's or call's `vars`, where the value cell is `*`. A new key, or a new value, is a row here in the same change.

## The gate registry and the landing check

`task gate-registry` (`gragas-dev gate check`) holds the registry under `gate/` to its schemas and to the tree: the exemptions and their expiry (below), the stand-in names, the shipped binary's closure, and the surface marks' base line to the base's. It reads every path the registry names, and the layer table and source tree, through the repository's root (`os.Root`), so a row that climbs out, starts at a root or follows a link out, or a `layers.yaml` that is a link out, learns nothing of a file outside. A missing or empty registry file fails it. It names the base in full, as refs/remotes/origin/main, where it reads the base's surface marks: git reads a bare origin/main as a tag of that name first, and a tag anyone can push would choose the base (gragas#589).

The landing check is `task landing`, which the lander runs on the merged tree before it squash-merges (gates.land.1, gragas#912), by `gragas-dev landing run`, which cuts the lander's environment to the hook's allowlist first (gragas#2169, gragas#2181): the push tier whole, `warm` and then `full` whole, each with its budget line (gragas#1619, gragas#1663), then the goldens journeys (`go test ./internal/journeys -run TestTheGoldens`), compared and never rewritten. The reviewer runs the goldens at review too. **The base is held too (gragas#1819):** `task landing` begins with `gragas-dev landing begin`, which prints the main the tree was merged with and refuses a tree that does not hold origin/main. The lander merges with `gragas-dev landing merge <N> --head <sha> --tested <that main>`, and with no other command: in one process it reads the pull request's own base (main, or release-1), fetches it, refuses when its tip is not the sha tested on (naming both) and only then runs `gh pr merge --squash --match-head-commit` through the program primitive of this command, output(), as every program of gragas-dev starts (go-proc's proc is held to internal/host/tool by arch.ports.6). The sha is the run's, handed in by the lander as `begin` printed it, so a tree merged again with the new main after a refusal passes nothing it was not tested on; `landing check --tested <sha>` is the same comparison with no merge. `gh pr merge --match-head-commit` pins the pull request's head and never the base, so with two landers the other could merge in between and land a tree no landing ran. A refused landing runs again on the new merged tree. What is left is one fetch's width: a merge by the other lander between this one's fetch and gh's merge. The alternative, one lock shared by both landers from the start of a run to the merge, is not built: it would hold one lander idle through a whole landing (the full tier takes up to an hour) to save a rerun only when main moves, and a lander that dies holding it would stall the other. There is no judge built from the base, no protected list and no stored verdict: gragas#912 deleted the landing and squash scripts, the protected list, the judge's closure list, the verdict files and `gragas-dev gate judge`, so a change to `gate/`, to a schema under `gate/schema/` or to the gate's code is the review's to read, and the merged tree's run is what proves it. The paths that can weaken a check are the review's by name, and the reviewer says in the verdict that each one the pull request touches was read: `gate/` with its schemas; the gate's code (`cmd/gragas-dev`, `internal/dev/gate`); `Taskfile.yml`, which says what every tier and `task landing` run; `hooks/` and the committed agent settings; `tools.yaml` and `tools/`; `lint/`; `.gitleaks.toml` and `suppressions.txt`; `LICENSE`; and every `testdata/` folder of goldens, where a rewrite made with `-update` is named in the pull request with its cause (the retired protected list's paths, carried over by gragas#912). The agent settings' denies stay: with no CI and no judge, the pre-push hook is the one check before main, and the denies are what stop an agent skipping it. #1025's check of a young release joins `task landing` with whichever of gragas#912 and its pull request lands second, and the release tier keeps its own.

`gragas check` reads a project's `gate/exemptions.yaml` when the project has one and lists what is wrong with it beside the rulebook's findings: a row listed twice, a rule that is not active, an expiry that is not a date or has passed, an `exemptions` that is not a list or a row that is not a mapping, and an exit that names no issue or file, leaves the project, or names a file the project does not hold (gates.exemptions.4). It reads the exit through the project's root, so an exit through a link to a file outside says the same whether that file is there or not (gragas#498). Its `--json` answer holds an `exemptions` object of `rows`, `next_expiry` and `findings`, for display. The comparison of an expiry with the day is made in one place, `internal/core/project`, and `task gate-registry` calls it itself, on the file it reads through the repository's root, with gragas-dev's own clock: it prints `exemptions: N, next expiry D` and fails on each finding, on a file it cannot read, and on a clock that names no day. Here it also holds each row's shape to its schema. It never runs the shipped check or reads its answer.

A pull request whose merge conflicts goes back to its builder, who merges main and pushes again. Regenerating a conflict that only a generator wrote (gates.protection.5) is not built since the squash script went with gragas#912 (gragas#464).

The check reads no text of `rulebook/`.

## The final run

Release 1 is merged by one final pull request from release-1, and before it lands, its run installs and approves a plugin on each machine the way a user would (gragas#2044). The release steps are `docs/self-check.md`, Releases; this run uses what they build.

**The freeze (gragas#2007).** main stands still from the final pull request's last merge of main into release-1 until that pull request lands. The pull request names the freeze when it opens, so every lead holds pushes to main, and the run's record below names it too, with the sha of that merge.

**The binary is the shipped one.** Each machine runs the gragas of the release archive for its system, as `release-build` made it, never a local build: on the Mac a release binary runs a plugin in wazero's interpreter, and only the shipped binary proves that it loads and runs one (gragas#2045). The plugin is golangci-lint's bundle from the birdtable/gragas-plugins release, taken by path.

**On each machine, in this order:**

1. Start from a home with no plugin approved: a new user account, or a new, empty home. On macOS and Linux that is `HOME` set to a new, empty folder with `XDG_STATE_HOME` unset; on Windows, `LOCALAPPDATA` set to a new, empty folder, since `HOME` moves nothing there. Approvals live in the state folder (`docs/settings.md`). `gragas plugin list` shows golangci-lint as not approved. A machine where the plugin was approved before the run does not count.
2. Add the bundle by path, from the rulebook the run checks with: `gragas plugin add <bundle folder>`, which shows each file and the lock entry, then the same line with `--apply`. Adding approves nothing.
3. Approve it once, by digest, on the command line: `gragas plugin approve golangci-lint@<version>` shows the digest, the tool and every grant, and ends on the line to type; that line, `gragas plugin approve golangci-lint@<version> --digest sha256:<digest> --apply`, records the approval. No prompt is answered, so a machine with no terminal runs the same steps (`docs/architecture.md`, 4.1).
4. The run: `gragas plugin list` shows golangci-lint approved, and `gragas check` over the project runs the plugin and ends green.

**The run's record**, on the final pull request, is one block a machine: the system, the release archive and its sha256 from the release's checksum file, the home the run started from, the birdtable/gragas-plugins release tag the bundle folder came from, the rulebook's commit, the project `gragas check` ran over and its commit, the approved digest that step 3 printed, and the closing word and exit of `gragas check`. The approved digest is the same in all three blocks, so the three machines are seen to have run the same bundle, and the tag holds it to the bundle that release rebuilds; a record that names no approved digest is not a run.

**Who runs which machine.** The fleet runs the Mac's leg and records it. Nobody in the fleet runs or asks for the Linux or Windows legs, and nothing waits on the fleet for them. Before the final pull request, the steps are tried once on the Mac from a home with no approval, with the golangci-lint plugin (gragas-plugins#11), and that dry run's record is on gragas#2044's pull request.

## What a repository gives `gragas check`

`gragas check` reads the project's own tool configs and its runner against the rules of the parts the project takes (gragas#927, gragas#929). Two one-line files in the project's `.gragas` folder say what it takes and builds for, until `gragas resolve` is built. Where the file `parts` is absent, nothing below is read and nothing is a finding.

- `parts` lists the part names, separated by spaces or commas.
- `systems` lists the systems the project builds for, one name for a GOOS and a GOARCH joined by a slash (linux, then amd64), separated by spaces, commas or lines. Each build and each lint member of the pre-push tier is asked for once per system. An entry that is not a pair Go builds for (the table is `internal/host/assets/audit/systems.yaml`) is a finding at its line. With none listed, one build and one lint member are asked for, and the report says so as a not-checked line, never silently.

The tier contract (#929) reads the project's Taskfile (the one go-task runs: its default names in its own order, each matched exactly against the folder's listing, so a host that folds case reads the same file) and the pre-push hook file, and runs nothing: no tier, no time budget. The table is data, `internal/host/assets/audit/tiers.yaml`: the tasks `pre-commit`, `pre-push`, `full` and `release`, the member each tier holds with the rule it cites, the hook files it looks for, and the land job (rulebook#55). `full` holds what the push leaves out: the tests, govulncheck (supply.scans.7) and `gragas check`. The land job is the task `landing`, which must call `pre-push` and then `full` as cmds with no key beyond `task`, `silent` and `timeout` (no `vars:`, which reach every member and can turn a member's skip on), so the hook's list is a declared subset of the land job's, and every member of both runs on the merged tree before main (gates.command.1). A missing `landing`, a skip on it, or a call left out or out of order is a finding. A finding names the file and the line, and the rule. It reports: a missing tier (and, with no Taskfile at all, that one finding only); a Taskfile read from its own file and from the files it `includes:` (an include is read as go-task reads it: `flatten: true` puts its tasks in the includer and not under its namespace, `excludes:` drops the tasks it names, and `aliases:` are further namespaces for it; a local include by its path in the repository; a remote one needs `checksum:` and, for a git address (`git::`, `git@`, or an https address whose path runs through `.git//`), a `ref=`, and one the check cannot read is a finding that names it, never an unannounced pass; a remote include is read through the `Remote` hook of the input, none by default); members reached through `deps:` and `task:` calls, which are read as a pool (`deps:` runs in parallel and go-task lets every dep finish, so a tier with two red members prints both) and held to what gates.command.12 asks of one: `failfast:` at the file or the task, or `--failfast` in a member, is a finding, since a red member would then stop the others; a member go-task does not run on every host or whose failure does not fail the tier (a command mapping with a key beyond `cmd`, `timeout`, `silent`, `set`, `shopt` and `vars`: `ignore_error`, `platforms`, `if`, `for`, `defer`, `task` beside `cmd`, and a cmd-level `env`, which go-task drops; a tier task with `ignore_error`, `platforms`, `if`, `status`, `sources` or `generates` (a `status:` whose first line is the guard `[ "{{.CLI_FORCE}}" != true ] && [ "{{.VAR}}" = 1 ]` (read with mvdan.cc/sh as one statement whose top node is an `&&` chain with those two tests leftmost: a tail inside the chain may stay, but a `||`, a `;`, a second line or a `&` after it is not the guard, since the line then ends green or runs on), with VAR declared in the file's own `vars:` as a literal string that is not `1` or `true` and holds no template, not set again by the guarded task, and not passed a value that may be `1` by a call on the way to it (go-task ranks a call's `vars:` above the file's and the task's; a literal string that is not `1` or `true` and holds no template is safe, and so is the forward `{{.VAR}}` of the variable itself, which go-task resolves in the forwarding task's own scope, so a task on the way whose own `vars:` set VAR to a value that may be `1` is held to the same rule), is a declared skip: --force runs the member whole and it is off until a caller passes VAR, so the commit's and the push's tiers hold it; a VAR that is a command (`sh:`), a template, a number, absent or set again by the task is read where go-task reads it, which the audit does not follow, so it fails closed; the release tier, which the table marks `whole`, holds none, except that where its task refuses to run without --force, by a precondition `[ "{{.CLI_FORCE}}" = true ]`, a `status:` that is the guard is excused, and a plain `status:`, `sources:` or `generates:` is not, since with go-task's gentle force (a `.taskrc.yml` or a `.env` turns it on) --force forces only the task it names and a task it calls is still judged by its own checks); the same keys on a task a tier calls (a `deps:` entry or a `cmds:` `task:` call, in the file or an included one), and on the call itself any key but `task`, `vars`, `silent` and `timeout` (`if`, `platforms`, `ignore_error`, and a `for:` the audit cannot read as one that runs: a `for:` runs the callee, which counts once, when it is a list with an item, a matrix whose every axis is one (written out or a `ref` to a variable of the file's own `vars:` that is one) or a `var:` that is one, and that no task or call on the way sets again, since go-task resolves a `for:` in the scope of the task that holds it, where that task's own `vars:` and a call's outrank the file's; an empty list, an empty or string variable, an empty axis, `sources` and anything else is a skip), each of which makes the called task's commands count for nothing and is named with the task (#1261); a remote include whose text is not the one its `checksum:` names; `set` holding `n` or `noexec` on a member, a tier task or the file, which makes go-task's shell run no command), which counts for nothing; ## The delegated cgroup

This note is for a run held to a memory limit someone set. gragas sets no memory limit of its own: `gragas check`'s read of golangci-lint's config and a tool run at the isolated level are held to a deadline and to no memory limit unless one is set, so they ask go-proc for no bound and run on every host, a Linux host with no delegated cgroup among them. Only a run with a limit set is held to one.

go-proc holds a run with a memory limit set. Where it holds it and what it does:

- **Linux, in a delegated cgroup:** go-proc holds the run's tree to its bound and reads its peak, but only in a cgroup that systemd delegated to the program.
- **Linux, with no delegated cgroup:** the run is refused by name before it starts. A check that asked for the run ends `not ready` in that refusal's words. Exit 4 means the call fits its shape and it is the host that is not set up, as with a missing input in spec S40. It never says "golangci-lint rules were not checked", which stays for a linter that is not there or a config the check refuses to hand it. Nothing is started, and a limit that was set is never dropped.
- **macOS and the BSDs:** the peak is judged after the run.
- **Windows:** the Job Object holds it.

To hold a limit on Linux, the fix is the host's, not a setting of gragas. Run gragas as a systemd user service with `Delegate=yes` and `DelegateSubgroup=app` (systemd 254 or later). The service's cgroup is then the program's to make children in, and gragas itself sits in its `app` child. A one-off run can be a transient service, `systemd-run --user --wait --pty --same-dir -p Delegate=yes -p DelegateSubgroup=app gragas check`. The user manager must have the memory controller delegated to it, as `user@.service` does by default on current distributions. The other way is the sandboxed level, which caps the whole run on every system.

The tests of a run with a limit ask go-proc the same question before they expect a run (`configtest.HoldOf`), never the system's name, so a host with no delegated cgroup holds the refusal, not the run. The tests of a run with no limit expect it to run on every host.

## The command generator

`gragas-new command [<group>] <verb>` shows the files a new command has: its package below `internal/cli/cmd/<family>` (the family is the group, or the verb of a flat command) with its row in Go, its operation in `internal/core/api`, and a transcript, a unit and a journey stub. A command that has a planned file in `internal/cli/planned` takes its row from it and the file is removed in the same run. `task gen` then joins the package (`internal/cli/root/join_gen.go`) and renders the documents; the generator names no hand-written file outside the new package and refuses a plan that does. With `--apply` it writes them; a name off the base list, a refused verb, a name the registry declares as built, a file that exists, or a group still in the old table of `internal/cli/root` is refused and nothing is written. A path of the plan is cleaned before the test, and one that still climbs (`..`) or is absolute is refused. A scaffold changes the registry, so after `task gen` the two goldens `internal/cli/root/testdata/help-commands.golden` and `internal/cli/root/testdata/readme-table.golden` are regenerated with `-update`, the diff read, and both listed as covers; the closing text says so. The golden example is `internal/dev/templates/command`. A test of `cmd/gragas-new`, in the `test-heavy` member at release and in `gate-tests`, runs the generator into a copy of the tree, built once, and checks that the copy builds, vets, that the generated files pass the linters the config enables, that the registry rules hold, and that its three stubs fail naming the command; a template that gives a global variable is its red case.

## The managed root files

The sync engine is gone (#911): no tool lays down root files from a template, a repository copies the starting configs from `presets/`. `.gitattributes`, `hooks/` and the secret scan's two configs stay hand-written, and a change to one is the review's to read.
