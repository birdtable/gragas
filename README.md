**Status: early.** The rules are in place, one preset is written, and the CLI is being built command by command. Nothing is released yet, so there is no version to pin.

## What it is

The name is from *Grágás*, "grey goose", the old Icelandic law book.

- **A rulebook.** Every rule says what must hold, why, where the reason comes from, and which tool checks it (`rulebook/`). The rules sit in layers (`base`, `lang`, `program`, `framework`, `data` and `cloud`) and in parts within them; a project is the base parts plus the parts it is built from.
- **Presets.** Shareable configs for the tools a project already runs (`presets/`), written by hand and tested with each tool's own test runner, except the Go lint file, which is generated from the rulebook's bindings and its hand-written settings file (see `CONTRIBUTING.md`). The golangci-lint one is written (`presets/golangci/`); the ESLint, tsconfig, ast-grep, Semgrep and Rego ones are planned. A project imports the presets for its parts in its own config files and adds its own rules on top, and each rule a preset holds names the rule ids it comes from.
- **A small CLI, `gragas`.** Every command is one row of a registry, and the table below is generated from it. It validates the rulebook, adds and changes rules with a history entry for each change, and runs `check` for the few things no linter config can hold: expired waivers, a binding rule switched off without a reason, drift from the base config, ratchets (`cmd/gragas`).

## What it is not

It is not a linter, a hook manager, a CI system or a tool installer. Projects keep running their own tools in their own hooks. Gragas supplies the presets and one extra check.

## Plugins

Gragas knows no tool. A tool is a plugin: code that implements gragas's plugin interface (five operations, plan, entries, findings, rank and preset) and says how to read and run that one tool. A person installs a plugin with `gragas plugin add`, approves it once on a machine, by its digest and its grants, and may write their own for any tool, in any language that builds to WebAssembly. The plugins for golangci-lint, ESLint, the TypeScript compiler and ast-grep, and the SDK, live in a repository of their own, birdtable/gragas-plugins; the engine, the contract and one fake plugin, `standin`, live here. A plugin proves itself with `gragas plugin test`. The design is in [the architecture](docs/architecture.md), section 4.1.

## The checks

`task pre-push` runs the commit-level checks on the machine that pushes, and the pre-push hook runs it before every push. There is no CI on a push or a pull request. Each check is a task of `Taskfile.yml`, in one of four tiers: `pre-commit` (the staged change reads and never rewrites, and holds no secret), `pre-push` (the pushed tree passes the commit-level members), `full` (every member the push leaves out, which landing runs on the merged tree) and `release` (a fresh clone of the tag passes, with what only a release proves). A tier's wall time is judged against a number in `gate/budgets.yaml`, printed with each run, and this page does not repeat it. `docs/checks.md` has the setup, the tiers and the gate.

The shared Go plumbing, the lock and the atomic write, comes from a private module.

## Development

To work on gragas you need Go, at the version `go.mod` names, and the pinned tools the preflight builds from `tools.yaml` (`task tools`). On Linux you also need tini.

tini is a minimal init, the one Docker's `--init` uses. gragas needs it on Linux because its tests that signal a process or a process group run inside a PID namespace (`unshare --pid`), where `go` is pid 1 and `go` reaps no orphan, so a test would see its orphan as a zombie. `internal/host/tool` is the package that needs it. Install it with `apt install tini`; on other distributions, install the package named tini. It is a development dependency only: people who use gragas never need it. `docs/checks.md` has the rest.

## Layout

| Path | Holds |
|---|---|
| `rulebook/<layer>/<part>/rules/*.yaml` | the rules, one file per concern |
| `rulebook/<layer>/<part>/tools.yaml` | the tools each part uses |
| `rulebook/parts.yaml` | the parts, their layers and what each builds on |
| `rulebook/schema/` | JSON Schemas for the YAML |
| `rulebook/rules.json`, `bindings.json` | generated from the YAML |
| `presets/` | the presets: written by hand, except the Go lint file presets/golangci-lint/.golangci.yml, which is generated from the bindings in the rule files and presets/golangci-lint/settings.yml |
| `cmd/gragas/` | the CLI's entry point |
| `internal/` | the CLI's packages, in layers: `docs/layers.md` |
| `layers.yaml` | the CLI's layer table; `docs/layers.md` and `.golangci.yml` (with `lint/base.yml` and `lint/project.yml`) are generated from it |
| `gate/` | the registry the checks and the landing read: members, budgets, baselines, verdicts |
| `docs/self-check.md` | the Hard rules gragas does not meet yet |
